Build the database-backed, multi-project Nuecagram service with installation-specific webhook secrets, Telegram group-admin onboarding, one-time management links, rotation, server-rendered management/admin UI, PostgreSQL/Exposed/Flyway, and production-ready docs/deployment. ## [BRIEF]
Type: Proposal
Source: github:49

Current understanding:
- Nuecagram is currently a single-secret, mostly stateless webhook relay with in-memory pipeline tracking.
- This task turns it into a hosted multi-project service where each installation owns its GitLab webhook secret, Telegram destination, mute state, and management lifecycle.
- The implementation spans database persistence, Telegram-admin onboarding, one-time management links, server-rendered management/admin UI, production deployment, and documentation.

Desired outcome:
- Operators can host one Nuecagram instance for multiple GitLab projects/installations.
- Each installation can be created, authenticated, managed, rotated, muted, and recovered without exposing plaintext secrets or management links.
- The service is production-ready with PostgreSQL persistence, Flyway migrations, health checks, secure CI/release flow, and documented deployment/rollback.

Constraints / non-goals:
- Keep the global Telegram bot token, but remove the global GitLab webhook secret as DB-backed installation auth lands.
- Do not leak secret fragments in logs, URLs, admin pages, or reverse-proxy access logs.
- Release Please should manage the version PR only; image publication, tag/release creation, and deployment must be quality-gated in the reviewed workflow.
- S1 is baseline only: schema, DB wiring, and readiness/liveness; do not prematurely redesign webhook/business flow in that slice.

Acceptance hints:
- PostgreSQL/Exposed/Flyway baseline lands first, then installation lifecycle, per-installation webhook auth, Telegram onboarding, management/admin UI, docs, CI, and protected deployment.
- Readiness must prove DB connectivity; blocking Exposed transactions must run on `Dispatchers.IO`.

## [GRILL]
- **Release trigger evidence**: `release.yml` uses Release Please with the default `GITHUB_TOKEN`. The tag workflow has no run for `v0.10.0`; the most recent Docker deploy run is `v0.9.5`. GitHub suppresses downstream workflow triggers for events created with `GITHUB_TOKEN`, so the current Release Please tag cannot trigger `docker-deploy.yml`.
- **Required correction**: S8 must consolidate image publication (and later protected deployment) into the Release Please workflow when a release is created, or invoke a reusable publish workflow directly. Do not add a broad PAT merely to re-enable tag-trigger recursion.
- **Pending decision**: use the consolidated Release Please workflow as the only publisher/deployer path; retain the tag workflow only as a manually dispatched/reusable workflow if useful.
- **Release-order contradiction**: Release Please normally creates the tag and GitHub Release when its release PR merges, but requirements say the GitHub Release comes only after quality gates and image publication. Release Please should manage only the version/changelog PR; a directly invoked publisher validates, pushes the immutable image, then creates the tag and GitHub Release.
- **Secret leakage surface**: `EventData.log()` logs the first and last four characters of webhook secrets. New flow must log no secret fragments and must exclude token-bearing paths from application and reverse-proxy access logs.
- **Management URL containment**: atomically exchange a valid URL token for a short-lived server-side session, then redirect to a token-free URL. CSP and `Referrer-Policy` do not remove tokens from history/access logs.
- **Telegram ingress**: validate `X-Telegram-Bot-Api-Secret-Token` independently from GitLab's `X-Gitlab-Token`; handle duplicate Telegram update IDs idempotently.
- **Command gap**: accepted admin-only `/mute` and `/unmute` are absent from S4, although mute persistence and webhook behavior are planned elsewhere.
- **Installation context impact**: installation UUID must travel through `EventData`, queueing, destination resolution, and every pipeline/job state API; current code uses request routing headers and bare numeric IDs.
- **Startup impact**: startup validation and Koin both require `NUECAGRAM_SECRET_TOKEN`; remove that requirement atomically with DB-backed authentication while retaining the global Telegram bot token.
- **Admin recovery constraint**: platform admins must not see plaintext management links. Recovery must be delivered through the verified Telegram-admin private flow.
- **Documentation evidence**: README teaches all three legacy `X-Nuecagram-*` headers; replace these with `X-Gitlab-Token` and fresh-install guidance.
- **PR alignment**: draft PR #48 deploys `latest` and lacks strict host verification/readiness/rollback. Close it and replace it with the reviewed S9 PR.
- **Canonical-state gap**: `[BRIEF]` is empty and task metadata predates the updated issue. Re-frame from issue #49 before implementation.
- **Docs decision**: use Zensical to build the Markdown documentation site published by GitHub Pages.
- **Dependency surface**: `gradle/libs.versions.toml` targets Ktor 3.5.1 and Kotlin 2.4.0. We must use Exposed and Flyway versions compatible with Kotlin 2.4.0.
- **Transaction scope**: Exposed `transaction {}` blocks are blocking; they must be dispatched on `Dispatchers.IO` when invoked from Ktor's asynchronous routing to avoid thread starvation in Netty.
- **Issue verification**: GitHub #49 explicitly requires PostgreSQL, Exposed, HikariCP, Flyway, immutable-image deployment, and readiness at `/nuecagram/health/ready`; S1 must include HikariCP and preserve the required readiness route rather than only adding arbitrary root-level probes.
- **Current ingress impact**: `WebHookService` authenticates one `NUECAGRAM_SECRET_TOKEN` and requires caller-controlled `X-Nuecagram-Chat-Id`/`X-Nuecagram-Topic-Id`; `EventData` carries and logs those values, while `WebhookRequestHandler` resolves its Telegram destination from them. S3 must replace this entire chain atomically with authenticated installation lookup and must remove partial secret logging.
- **State collision impact**: `WebHookService` keys pipeline/job tracking maps solely by numeric pipeline/build IDs. S3 must namespace every tracking operation by installation ID to prevent cross-installation message edits.
- **Startup and test impact**: `Application.kt`, `ConfigWithSecrets`, and Koin configuration all require the global webhook secret; tests start the same modules manually. Removing that secret requires coordinated application, DI, and test changes.
- **Operations evidence**: `compose.yaml` has no PostgreSQL service or persistent database volume. The Docker health check probes `/`, not the required DB-backed readiness route. The tag workflow publishes `latest`, and Release Please tags cannot invoke it when created with `GITHUB_TOKEN`; both are incompatible with the issue's immutable, quality-gated deployment requirement.
- **Documentation/script impact**: README and `scripts/create_gitlab_webhook.sh` still document legacy routing headers and a deployment-specific webhook URL. S7 must replace them with generic installation onboarding and GitLab's native secret token.
- **S3 verification audit**: runtime auth correctly resolves `X-Gitlab-Token` to `InstallationContext`, `EventData.log()` contains no credential, and pipeline/job maps use installation-scoped keys. But `resolveWebhookInstallation()` discards the verified secret ID and `WebHookService` never calls `confirmWebhookSecret()`, so a rotated secret cannot be confirmed by its first valid webhook. The remaining optional `ConfigWithSecrets.secretToken`, test-only mock value, unused old-header constants, and all 26 raw `.http` request fixtures preserve obsolete contract vocabulary. Existing focused coverage only exercises a valid DB-issued token through legacy smoke tests plus a pure rate-limit check; it lacks the S3-specified invalid/expired/superseded, caller-header isolation, installation collision, mute, payload, and no-secret-log assertions. `X-Forwarded-For` is currently accepted as a rate-limit identity without a trusted-proxy boundary, allowing caller spoofing.
- **S4b1 code reality**: `TelegramUpdateHandler` now routes `/status` through private-bootstrap lookup, `TelegramService.chatMemberStatus()`, installation UUID lookup, and stored-chat ownership before returning credential-free status text. Rejected requests currently send safe guidance and do not call `writeAuditEvent()`, but there is no direct no-rejected-audit assertion yet.
- **S4b1 failure edge**: `TelegramServiceImpl.chatMemberStatus()` throws on non-200 Telegram API responses and `TelegramUpdateHandler` does not catch it. Treat admin lookup failure as authorization failure with safe guidance, not a webhook 500, unless product explicitly wants Telegram retries for transient API outages.
- **S4b2 impact surface**: the remaining `/digest`, `/test`, `/mute`, and `/unmute` commands should reuse the existing S4b1 gate instead of duplicating parse/bootstrap/admin/ownership checks. `InstallationRepository.setMuted()` and `writeAuditEvent()` already exist; `MockTelegramService.sentMessages()` can verify stored-destination delivery for `/test`.
- **S4b2 audit constraint**: successful mutation commands must write audit rows, while unauthorized, malformed, unknown, duplicate-update, and wrong-chat requests must remain no-op/no-audit. The current duplicate update guard is global on `telegram_updates.update_id` and executes before command handling, so duplicate command tests should assert only one outbound effect and one audit/mutation.
- **S7 branch reality**: `feat/github-49-hosted-onboarding` is current through merged S5/S6 code, but its tracked `WORK.md` checkboxes/log are stale and still show S5/S6 incomplete. Planning must correct canonical slice state before starting S7.
- **Documentation drift**: `README.md`, `compose.yaml`, `scripts/create_gitlab_webhook.sh`, and `scripts/get_gitlab_webhook.sh` still describe the removed global token/caller-routing contract, contain deployment-specific examples, and omit Telegram-admin onboarding, management/admin UI, PostgreSQL, and DB-backed readiness.
- **Runtime env contract for S7**: hosted code requires `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `PLATFORM_ADMIN_PASSWORD_HASH`, `DATABASE_URL`, `DATABASE_USER`, and `DATABASE_PASSWORD`; optional controls are `PORT` and `NUECAGRAM_BASE_PATH`. Generic env and compose files must use placeholders only and must not reintroduce `NUECAGRAM_SECRET_TOKEN`.
- **Public URL blocker**: Telegram setup/management messages derive public URLs from `application.json` (`host=localhost`) rather than an environment-configurable public origin. Documentation cannot provide a working production setup without adding a `NUECAGRAM_PUBLIC_URL` setting or requiring a rebuilt resource, which conflicts with environment-only deployment.
- **Compose/ops scope**: S7 needs app and PostgreSQL services, a persistent DB volume, app readiness health check, DB health dependency, and private `.env` consumption. Backup/restore must use PostgreSQL-native `pg_dump`/`pg_restore`; rollback must pair the previous immutable image with a compatible DB backup and must not promise Flyway down-migrations.
- **Webhook script contract**: GitLab's native `token` field supplies `X-Gitlab-Token`; scripts must read arguments/environment, fail on missing inputs, and never embed personal tokens, domains, chat IDs, topic IDs, or custom `X-Nuecagram-*` headers.
- **Docs site evidence**: Zensical uses `zensical.toml`, `docs/`, `zensical build`, and a GitHub Pages workflow. The Pages workflow belongs to S7; release/image/deployment workflow changes remain S8/S9.
- **Exposed contradiction**: Exposed dependencies are installed and `Database.connect(source)` is called, but all installation/session/audit persistence uses raw JDBC in `InstallationRepository`; there are no Exposed tables, transactions, or repository queries. Public docs must not claim an Exposed-backed repository until this brief/implementation mismatch is resolved.
- **Resolved Exposed decision**: migrate persistence to real Exposed tables/transactions before S7. This is a corrective implementation slice, not documentation work; blocking Exposed transactions remain on `Dispatchers.IO` through the database boundary.
- **Resolved public-origin model**: `https://android.nweca.com/nuecagram` can host Nuecagram behind a path-preserving reverse proxy. Treat a new `NUECAGRAM_PUBLIC_URL` as the complete external application root, move GitLab ingress from `/webhook` to the base-path-aware `/nuecagram/webhook`, and generate webhook/management URLs relative to that one public root. Because this is a fresh deployment, no legacy root `/webhook` compatibility route is required.
